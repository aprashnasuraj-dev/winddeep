- **Confirmed library defect:** C-002 — seven distinct malformed encrypted-keystore input variations trigger recoverable Go panics in the certified target decoder; the failure is in target input handling, not just CI YAML. A test which catches or expects a panic does not prove a remote vulnerability; a Go test marked PASS may intentionally characterize an unsafe outcome.

## 1. C-002 — Malformed encrypted keystore parsing (highest verified local robustness concern)

**Source and input path.** [`accounts/keystore/keystore.go:437–453`](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/keystore.go#L437-L453) `KeyStore.Import(keyJSON,passphrase,newPassphrase)` invokes [`DecryptKey`:200–227](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/passphrase.go#L200-L227) → `decryptKeyV3` → [`DecryptDataV3`:240–273](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/passphrase.go#L240-L273) → [`getKDFKey/ensureInt`:330–365](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/passphrase.go#L330-L365). `GetKey` also reads a locally stored filename and invokes `DecryptKey` ([passphrase.go:82–92](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/passphrase.go#L82-L92)).

**Exact causes.** `cryptoJSON.KDFParams["salt"].(string)` and `["prf"].(string)` lack type checks; `ensureInt` assumes `float64` when not `int`; `DecryptDataV3` slices `derivedKey[16:32]` and initializes AES-CTR with the supplied IV without prior explicit length validation. A validly decoded but incorrectly sized IV can panic in the cipher API. The `dklen=8` case apparently succeeds because Go's two-index slicing can extend beyond the slice length into available backing-array capacity; **this is not evidence that only eight derived bytes were used cryptographically**. Measure both `len` and `cap` before making key-strength claims.

**Executed evidence.** [CI run 41729221393, attempt 2](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41729221393), job `126245206204`, certified scratch Go command `go test -count=1 -timeout=5m -run '^TestWorkerCKDFMalformedInputCharacterization$' -v ./accounts/keystore`: exit **1**, owing to an incorrect strict expectation that `dklen=8` must error. The valid control succeeded; `invalid_iv_length`, `missing_salt`, `numeric_salt`, `string_dklen`, `missing_n`, `missing_pbkdf2_prf`, `numeric_pbkdf2_prf` each produced a **captured Go panic**; `invalid_cipher`, `invalid_mac_hex`, `invalid_scrypt_n` returned ordinary errors. This is **7 + 3 + 1 = 11** malformed cases, plus valid control. Captured panic ≠ observed uncontrolled whole-process termination.

**Counterexample to remote exploitation.** The default RPC modules are only `net` and `web3` ([node/defaults.go:56–60](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/node/defaults.go#L56-L60)). [`PrivateAccountAPI.ImportRawKey`:386–397](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/internal/ethapi/api.go#L386-L397) takes a hex private key and calls `ImportECDSA`, not the encrypted JSON API. An attacker must therefore arrange local file parsing or a nondefault application integration. No RPC attacker path, theft, unauthorized signature or actual outage was observed.

**Recommended fix (concrete).** Reject KDF missing/wrong-typed parameters with error returns before crypto operations; range-check scrypt `N,r,p` and PBKDF2 `c`, `dklen`, and resource budgets. After KDF, check `len(derivedKey) >= 32`, not capacity. Require `len(iv)==aes.BlockSize` for AES-CTR. For legacy-file compatibility, explicitly document allowed KDF params instead of silently ignoring short declared lengths. Return errors via `Import`, `GetKey` and `DecryptKey`; defensive API-level recover is supplementary. Add regression for valid encrypted import, missing salt, wrong-typed fields, short IV, wrong password, short lengths `0,8,16,31,32` and large work factors.

**Latest work and gap.** [C fixture](https://github.com/aprashnasuraj-dev/winddeep/blob/electroneum-sc-master-audit/reports/electroneum/C/test_keystore_kdf_test.go) added `TestWorkerCImportMaliciousJSON`, with valid local import, missing-salt malformed import, and negative unsupported-cipher control. The active C workflow currently selects only `TestWorkerCKDFMalformedInputCharacterization`; **import integration remains not executed**. [C run 41732938082](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41732938082) certified bootstrap, signing and keystore characterization steps completed; sustained signing fuzz is in progress. Do not start overlapping C CI.

## 2. E-010 and E-004 — Public transaction-receipt API consistency

**Production call chain.** [`internal/ethapi/api.go:1571–1626`](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/internal/ethapi/api.go#L1571-L1626) `GetTransactionReceipt` obtains `tx,blockHash,blockNumber,index` from `GetTransaction`, then separately obtains `receipts` from `GetReceipts`, checking length but **not** `receipts[index].TxHash == requestedHash`. It serializes the *requested* `transactionHash` along with `receipt.Status`/logs/bloom. On London non-zero-fee path, `HeaderByHash` error is checked, but `header` is dereferenced without checking nil. [`eth/api_backend.go:99–101`](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/eth/api_backend.go#L99-L101) returns `GetHeaderByHash(hash),nil`; [`eth/api_backend.go:187–189`](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/eth/api_backend.go#L187-L189) returns receipts from the blockchain by hash.

**Threat and counterexamples.** A custom backend or a chain database inconsistency could produce a receipt whose index/hash disagrees with the transaction lookup, misleading an exchange that trusts a single response. A missing header with present receipt could panic. However, shipped `rawdb.ReadTransaction` checks canonical transaction placement and normal chain reorganization keeps coherent hash-indexed data; a transaction submitting user cannot automatically force backend inconsistency. **Normal production reachability and end-to-end financial harm are unproven.**

**Tests actually contributed.** [`E/test_rpc_receipt_cases_test.go`](https://github.com/aprashnasuraj-dev/winddeep/blob/electroneum-sc-master-audit/reports/electroneum/E/test_rpc_receipt_cases_test.go) constructs a synthetic `Backend` with (i) coherent canonical positive response, (ii) mismatched `Receipt.TxHash` with valid index, (iii) missing London header while all other receipt data remains. This executes the actual `PublicTransactionPoolAPI.GetTransactionReceipt`, not a copied arithmetic model. The first workflow edit produced malformed YAML and **zero jobs** ([failed 41739280280](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41739280280)); corrected workflow commit `c11dba84576f76fe11130ec59a5d9c4c82be65ee` began [E CI 41739456493](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41739456493). Certified bootstrap, rawdb baseline/mutation/restore, and new receipt test step all reported **success**, with 60-minute canonical rawdb fuzz in progress at checkpoint. **Full assertion logs pending**; pass means test characterized one of its permitted outcomes, not automatically that an exploit was proven.

**Remediation.** Fail closed unless `tx!=nil`, `receipt!=nil`, `receipt.TxHash==hash`, `tx.Hash()==hash`, matching block/index and a nonnil `header` with valid `BaseFee` under London. Consider canonical block revalidation at response time and return a structured reorg/inconsistency error instead of a partially coherent receipt. Add backend-race, reorg-and-requery, N-confirmation and deposit-credit independent-oracle tests; don't invalidate legitimate pending semantics.

## 3. B — QBFT round-domain and high-round consistency

**Verified serialization/runtime collision.** [`consensus/istanbul/engine/engine.go:61–66,101–105`](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/consensus/istanbul/engine/engine.go#L61-L105) `CommitHeader` passes `round` to `writeRoundNumber`, which stores `uint32(round.Uint64())`. [`PrepareCommittedSeal`:630–634](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/consensus/istanbul/engine/engine.go#L630-L634) signs `QBFTHashWithRoundNumber(round uint32)`. The existing certified `TestWorkerBRoundDomainCollision` fixture successfully constructed otherwise equal synthetic headers for round `0` and `2^32`, signed the round-0 digest with 3/4 synthetic validator keys, and demonstrated the encoded high-round header verifies the same seals. [B run 41675220241](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41675220241) completed with certified Go suites and historical fuzz counts 5,334,036 + 44,789,949 = **50,123,985**.

**Open reachability counterexample.** A below-threshold outsider cannot supply arbitrary accepted consensus rounds. [`core/roundchange.go:120–130`](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/consensus/istanbul/core/roundchange.go#L120-L130) caps round-change jumps to current + `MaxFutureRoundGap` and validators must authenticate. Reaching `2^32` for one sequence through real network conditions is unsupported by evidence. **Do not label this a forged finality exploit.**

**New `2^63/2^64` family.** [`core/roundchange.go:215–229,328–339`](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/consensus/istanbul/core/roundchange.go#L215-L339) selects unsigned `uint64` round map keys by converting to `int64`; values >=2^63 can become negative. `NewRound` and `Add` use `Round.Uint64()` as map key; rounds `0` and `2^64` alias. The separate source `core.go:startNewRound` tests `round.Uint64()==0`, so a theoretical high-round reset follows the same alias. New [`B/test_roundchange_arithmetic_test.go`](https://github.com/aprashnasuraj-dev/winddeep/blob/electroneum-sc-master-audit/reports/electroneum/B/test_roundchange_arithmetic_test.go) contains actual `core` Go assertions for normal small rounds, signed `2^63` discrepancy, and `0`/`2^64` map alias, with independent full-width expected values. Integrated in class B workflow commit `a8601c5ed0e536ec151f12b3540b77c49fbda61b`; [B run 41739785577](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41739785577) started, result pending. This is a state-machine arithmetic fixture, NOT proof authenticated validators can reach such rounds.

**Fix direction.** Define and enforce consistent maximum round at *all* consensus input boundaries (bounded positive integer domain, with checked conversions), or use lossless `big.Int` representation for map keys, proposer selection, round reset, and serialization. A protocol-level change to signing encoding must be versioned/consensus-coordinated, not unilaterally deployed. Add tests for `0,1,2^32-1,2^32,2^63-1,2^63,2^64`, positive/negative controls, trusted validator authentication, F+1 thresholds and future-round rejection.
