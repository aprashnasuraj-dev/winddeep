# Worker C — Evidence-backed candidate findings

## C-001 — Mnemonic returned by explicitly exposed private RPC wallet initialization
- **Rank:** 1 (conditional exposure, potentially high impact); **severity if proven:** HIGH; **confidence:** MEDIUM in source behavior, LOW in attacker reachability; **status:** OPEN.
- **Certified source:** [internal/ethapi/api.go:563-583](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/internal/ethapi/api.go#L563-L583), `PrivateAccountAPI.InitializeWallet`. This obtains a caller-selected wallet URL, generates 256-bit entropy, converts it to a mnemonic, derives a seed with an empty passphrase, and returns the mnemonic along with `wallet.Initialize(seed)` for `*scwallet.Wallet`.
- **Attacker prerequisites:** An externally reachable `personal_initializeWallet` endpoint (the default HTTP/WS module lists exclude `personal`); a compatible `scwallet` hardware wallet; wallet initialization accepted for caller-selected URL; RPC transport permits method; attacker can receive response. No live wallet or public endpoint was tested.
- **Suspected invariant:** Lower-privilege RPC callers must not receive newly generated wallet recovery phrases or initialize another user's device without explicit local approval. If exposed and accepted, caller receives the generated mnemonic. This is not proof of theft of an existing wallet: the phrase is generated for a newly initialized wallet, and hardware initialization may require physical authorization.
- **Observed source evidence:** Method returns `mnemonic, wallet.Initialize(seed)` with no password argument or explicit `ExtRPCEnabled` guard. **Inference:** External RPC can invoke it if the private namespace is explicitly exposed; hardware device may reject unauthenticated initialization.
- **Strongest defeating controls:** `personal` not exposed by default; `s.am.Wallet(url)` may reject URL; `scwallet.Wallet.Initialize` may enforce device interaction; transport registration may restrict method.
- **Exact next falsification:** Trace `scwallet.Wallet.Initialize`, wallet URL selection and RPC method registration on immutable source; in a certified isolated fixture with a synthetic/mock compatible wallet and explicit `personal` exposure, test default namespace rejection, unknown wallet rejection, hardware approval denial, and permitted initialization; assert no mnemonic on denied paths. Compare with local IPC. Do not use actual device or real secrets.
- **Impact if proven:** Recovery phrase disclosure for a wallet newly initialized by an unauthorized caller, potentially compromising future deposits to that wallet. No real asset movement demonstrated.

## C-002 — Malformed keystore KDF field panics and short-length acceptance

- **Status:** OPEN / TESTING, **not CONFIRMED as attacker-reachable security vulnerability**. Severity if remotely reachable: potentially MEDIUM for service availability; local malformed-file acceptance alone has lower demonstrated severity. Confidence HIGH in isolated parser behavior, LOW in external attack reachability.
- **Certified source:** [`accounts/keystore/passphrase.go:240-273,330-365`](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/passphrase.go); immutable Windeep commit `7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0`; tree `de7f3c75a2db7e87a89918f1257820703d5b731e`. `getKDFKey` uses unchecked type assertions for `salt` and PBKDF2 `prf`, `ensureInt` assumes `float64` fallback, and `DecryptDataV3` slices derived-key material. `aesCTRXOR` can panic on invalid IV length.
- **Actual deterministic evidence:** [GitHub Actions run 41729221393](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41729221393), job `126241881435`, ran `go test -count=1 -timeout=5m -run '^TestWorkerCKDFMalformedInputCharacterization$' -v ./accounts/keystore` on certified bootstrap, scratch source. Valid baseline decrypted. Seven malformed cases produced captured panics (`invalid_iv_length`, `missing_salt`, `numeric_salt`, `string_dklen`, `missing_n`, `missing_pbkdf2_prf`, `numeric_pbkdf2_prf` = seven); three cases returned normal errors (`invalid_cipher`, `invalid_mac_hex`, `invalid_scrypt_n`). `short_dklen=8` unexpectedly decrypted (no panic/error), so the strict negative-control subtest failed and Go exited 1; fuzz was skipped. Log evidence distinguishes target parsing responses from the test assertion; job failure is **not itself an exploited defect**.
- **Attacker prerequisites:** Adversary must cause the process to parse crafted encrypted keystore JSON at a privilege boundary; none of the default remote RPC exposures has yet been shown to permit this without user control. There was no live wallet, private key, network exploitation, unauthorized signature or secret disclosure.
- **Suspected invariant:** malformed or undersized KDF parameters should yield controlled errors rather than panic or transparently change accepted key derivation parameters. Actual library behavior differs, but risk of process-wide crash and remote reachability require a caller and process-boundary reproduction.
- **Strongest counterexample:** encrypted keystore import may be local-user-only and safely isolated; Go panic may only affect user-initiated loading and not any remotely influenced path. `short_dklen` acceptance may result from capacity-backed slicing rather than effective entropy reduction; do not classify it as a cryptographic bypass without validating derived-key internals.
- **Next falsification:** trace all production `DecryptKey` / `DecryptDataV3` callers through public/private RPC exposure and authentication; run a certified synthetic `KeyStore.Import` fixture with malformed JSON, capturing panic propagation at API boundary, compare independent JSON/KDF validation oracle and a fail-closed scratch mutation. Keep existing exact failing fixture until its expectation and observed short-dklen acceptance are resolved transparently.

## C-002 — Verified decoder panic evidence and reachability assessment (2026-11-04)

**Classification:** CONFIRMED malformed-input **library behavior**, OPEN as an **attacker-reachable security vulnerability**. The precise demonstrated weakness is that malformed local encrypted keystore JSON can induce recovered Go panics in the certified decoder. Remote RPC exploitability, process-wide service loss, wallet-key compromise and ETN theft have NOT been reproduced. A potentially affected workflow is an operator importing a third-party encrypted keystore file; that threat requires the attacker-controlled file to reach the wallet application.

### 1. Vulnerability Detail with Proof of /electroneum-sc Git Codes/Sources

- **Immutable source identity:** Windeep commit `7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0`, Git tree `de7f3c75a2db7e87a89918f1257820703d5b731e`; upstream `3aeb14db0d6384243302f3a025bdff904dc28bf6`; archive provenance SHA256 `3ca62ab9c6951ea26cb13615d67255940e176522126f2ca7a157bf4035329d7b` (not re-hashed).
- **Untrusted input entry path, source traced:** [`KeyStore.Import`, keystore.go:437–453](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/keystore.go#L437-L453) accepts encrypted `keyJSON []byte` and calls [`DecryptKey`, passphrase.go:200–227](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/passphrase.go#L200-L227), then `decryptKeyV3` -> [`DecryptDataV3`, passphrase.go:240–273](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/passphrase.go#L240-L273) -> [`getKDFKey`/`ensureInt`, passphrase.go:330–365](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/passphrase.go#L330-L365). Neither `Import` nor `DecryptKey` has a visible `recover` around these operations.
- **Root cause:** `getKDFKey` uses unchecked `.(string)` assertions for `salt` and PBKDF2 `prf`; `ensureInt` assumes a non-`int` value must be `float64`, and `DecryptDataV3` fails to enforce `len(iv)==16` before AES-CTR. The crypto decoder slices `derivedKey[16:32]` without first checking `len(derivedKey)>=32`; Go slicing can extend beyond `len` up to `cap`, so the `dklen=8` success is not proof of weak-key entropy or key disclosure.
- **Live production counterexample:** [node/defaults.go:56–60](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/node/defaults.go#L56-L60) defaults HTTP/WS RPC to `net`, `web3` only. [`PrivateAccountAPI.ImportRawKey`, api.go:386–397](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/internal/ethapi/api.go#L386-L397) accepts hex ECDSA key material through `ImportECDSA`, **not** encrypted `keyJSON`. No default remote JSON keystore-import route was established.

### 2. Possible Impact

- **Demonstrated:** the isolated decoder panics on seven malformed test inputs instead of returning structured errors, which violates input-validation robustness. A caller that does not recover a Go panic can terminate its process, potentially interrupting a local wallet session or wallet service. The actual exported import method's propagation is **source-traced but awaits a separate executed integration fixture**.
- **Attacker prerequisites:** local or application-level ability to supply a malicious encrypted keystore file that a wallet operator/application imports or attempts to decrypt. A remote RPC method accepting the file, or theft of existing secrets, was **not found** in the inspected default exposure; this does not establish universal absence of custom integrations.
- **Severity:** conditional local/application denial-of-service, *not* a demonstrated remote wallet takeover, transaction signing bypass, asset theft or default remotely exploitable chain-node bug. Network-wide consensus safety is not implicated by this evidence.

No uncontrolled process termination or real private keys used.
- **Latest characterizing test improvement:** [C/test_keystore_kdf_test.go](https://github.com/aprashnasuraj-dev/winddeep/blob/electroneum-sc-master-audit/reports/electroneum/C/test_keystore_kdf_test.go) commit `d7ba9ba64502a5d6e9ce5cac6ee7606ed294abe9` retains the unexpected short-key acceptance and logs `len`/`cap` instead of falsely claiming a safe rejection. ### 4. Recommendation

1. Replace KDF map type assertions with validated typed conversions and explicit missing/type errors; avoid `ensureInt` float-to-int overflow/NaN/infinity/negative conversion. Validate salt, scrypt `N,r,p`, PBKDF2 `c,prf`, and `dklen`; reject unsupported KDFs and excessive work factors before allocation.
2. Before indexing or slicing a derived key, check `len(derivedKey)>=32` (never rely on `cap`). For V3 AES-CTR enforce `len(iv)==aes.BlockSize`; return an error rather than reaching `cipher.NewCTR` with an invalid IV. Preserve backwards compatibility by documenting legitimately supported legacy lengths, and reject those that fail the required 32-byte encryption/MAC material invariant.
3. For every `DecryptKey` caller, including `KeyStore.Import` and `keyStorePassphrase.GetKey`, propagate structured parsing errors; a top-level panic recovery may protect an application's request boundary but should not replace validation.
4. Expand certified regression coverage: actual exported `KeyStore.Import` valid/missing-KDF-salt/bad-cipher controls; wrong-password and valid-MAC invalid-IV; PBKDF2 missing/typed `prf`; derived length `0,8,16,31,32`, with `len` and `cap` output; high KDF-resource parameters; independent error-vs-panic oracle. Run fail-on-panic regression on a **disposable modified copy only** when testing a defensive patch. Record whether the full import path panics before promoting this to a confirmed application vulnerability.
5. Protect externally reachable API integrations separately: do not expose arbitrary encrypted keyfile import to untrusted clients, avoid default `personal` exposure, and require explicit authorization and rate/resource limits on any import service.

**Classification guard:** This four-part technical analysis belongs **only in the C candidate log** until the exported import path is dynamically proven attacker-reachable with concrete application harm; do not transfer it to the dedicated four-heading CONFIRMED vulnerability report solely because a characterization CI returned a failure.
