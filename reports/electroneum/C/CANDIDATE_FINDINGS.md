# Worker C — Evidence-backed candidate findings

## C-001 — Mnemonic returned by explicitly exposed private RPC wallet initialization
- **Rank:** 1 (conditional exposure, potentially high impact); **severity if proven:** HIGH; **confidence:** MEDIUM in source behavior, LOW in attacker reachability; **status:** OPEN.
- **Certified source:** [internal/ethapi/api.go:563-583](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/internal/ethapi/api.go#L563-L583), `PrivateAccountAPI.InitializeWallet`. This obtains a caller-selected wallet URL, generates 256-bit entropy, converts it to a mnemonic, derives a seed with an empty passphrase, and returns the mnemonic along with `wallet.Initialize(seed)` for `*scwallet.Wallet`.
- **Attacker prerequisites:** An externally reachable `personal_initializeWallet` endpoint (the default HTTP/WS module lists exclude `personal`); a compatible `scwallet` hardware wallet; wallet initialization accepted for caller-selected URL; RPC transport permits method; attacker can receive response. No live wallet or public endpoint was tested.
- **Suspected invariant:** Lower-privilege RPC callers must not receive newly generated wallet recovery phrases or initialize another user's device without explicit local approval. If exposed and accepted, caller receives the generated mnemonic. This is not proof of theft of an existing wallet: the phrase is generated for a newly initialized wallet, and hardware initialization may require physical authorization.
- **Observed source evidence:** Method returns `mnemonic, wallet.Initialize(seed)` with no password argument or explicit `ExtRPCEnabled` guard. **Inference:** External RPC can invoke it if the private namespace is explicitly exposed; hardware device may reject unauthenticated initialization.
- **Strongest defeating controls:** `personal` not exposed by default; `s.am.Wallet(url)` may reject URL; `scwallet.Wallet.Initialize` may enforce device interaction; transport registration may restrict method.
- **Exact next falsification:** Trace `scwallet.Wallet.Initialize`, wallet URL selection and RPC method registration on immutable source; in a certified isolated fixture with a synthetic/mock compatible wallet and explicit `personal` exposure, test default namespace rejection, unknown wallet rejection, hardware approval denial, and permitted initialization; assert no mnemonic on denied paths. Compare with local IPC. Do not use actual device or real secrets.
- **Impact if proven:** Recovery phrase disclosure for a wallet newly initialized by an unauthorized caller, potentially compromising future deposits to that wallet. No real asset movement demonstrated.

## C-002 — Malformed keystore KDF field panics and short-length acceptance

- **Status:** OPEN / TESTING, **not CONFIRMED as attacker-reachable security vulnerability**. Severity if remotely reachable: potentially MEDIUM for service availability; local malformed-file acceptance alone has lower demonstrated severity. Confidence HIGH in isolated parser behavior, LOW in external attack reachability.
- **Certified source:** [`accounts/keystore/passphrase.go:240-273,330-365`](https://github.com/aprashnasuraj-dev/winddeep/blob/7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0/vendor/electroneum-sc/accounts/keystore/passphrase.go); immutable Windeep commit `7eb84ee39bd01eaaf1f64afbd871b06c85ff3bb0`; tree `de7f3c75a2db7e87a89918f1257820703d5b731e`. `getKDFKey` uses unchecked type assertions for `salt` and PBKDF2 `prf`, `ensureInt` assumes `float64` fallback, and `DecryptDataV3` slices derived-key material. `aesCTRXOR` can panic on invalid IV length.
- **Actual deterministic evidence:** [GitHub Actions run 41729221393](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41729221393), job `126241881435`, ran `go test -count=1 -timeout=5m -run '^TestWorkerCKDFMalformedInputCharacterization$' -v ./accounts/keystore` on certified bootstrap, scratch source. Valid baseline decrypted. Seven malformed cases produced captured panics (`invalid_iv_length`, `missing_salt`, `numeric_salt`, `string_dklen`, `missing_n`, `missing_pbkdf2_prf`, `numeric_pbkdf2_prf` = seven); three cases returned normal errors (`invalid_cipher`, `invalid_mac_hex`, `invalid_scrypt_n`). `short_dklen=8` unexpectedly decrypted (no panic/error), so the strict negative-control subtest failed and Go exited 1; fuzz was skipped. Log evidence distinguishes target parsing responses from the test assertion; job failure is **not itself an exploited defect**.
- **Attacker prerequisites:** Adversary must cause the process to parse crafted encrypted keystore JSON at a privilege boundary; none of the default remote RPC exposures has yet been shown to permit this without user control. There was no live wallet, private key, network exploitation, unauthorized signature or secret disclosure.
- **Suspected invariant:** malformed or undersized KDF parameters should yield controlled errors rather than panic or transparently change accepted key derivation parameters. Actual library behavior differs, but risk of process-wide crash and remote reachability require a caller and process-boundary reproduction.
- **Strongest counterexample:** encrypted keystore import may be local-user-only and safely isolated; Go panic may only affect user-initiated loading and not any remotely influenced path. `short_dklen` acceptance may result from capacity-backed slicing rather than effective entropy reduction; do not classify it as a cryptographic bypass without validating derived-key internals.
- **Next falsification:** trace all production `DecryptKey` / `DecryptDataV3` callers through public/private RPC exposure and authentication; run a certified synthetic `KeyStore.Import` fixture with malformed JSON, capturing panic propagation at API boundary, compare independent JSON/KDF validation oracle and a fail-closed scratch mutation. Keep existing exact failing fixture until its expectation and observed short-dklen acceptance are resolved transparently.
