## Mechanism, controls and strongest counterexample
Shipped `core/rawdb/accessors_indexes.go` `ReadTransaction` / `ReadReceipt` use current canonical block hash at the lookup height and search canonical body/receipts. A transaction can appear in both competing blocks; therefore changing the canonical block **does not necessarily make that transaction orphaned**. The new deterministic fixture uses height 73, blocks A/B, the identical transaction hash in both bodies, different success/failure receipts, and A -> B -> A transitions. The independent oracle expects canonical block identity and receipt status to follow the current canonical hash. The negative variation replaces B's body with a different transaction and expects null lookup for the original transaction. Mutation-sensitivity comes from the existing workflow's intentionally broken canonical lookup; injected bugs are not target findings.

The strongest counterexample to a generic orphaned-receipt claim is that the same transaction can remain canonical in the replacement block. The strongest counterexample to external miscredit is a relying exchange that rechecks block canonicality and confirmations before crediting.
