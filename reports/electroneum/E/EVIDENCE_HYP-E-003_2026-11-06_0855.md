## Source-to-decision chain and competing explanations
1. `/electroneum-sc/eth/api_backend.go:265-268`: public backend `GetTransaction` delegates to `rawdb.ReadTransaction`, returning nil error even if transaction absent.
2. `/electroneum-sc/core/rawdb/accessors_indexes.go:~80-117`: `ReadTransaction` uses tx lookup height, current canonical hash and matching canonical body transaction. This rejects an orphan if lookup begins **after** canonical switch (strongest existing defense).
3. `/electroneum-sc/internal/ethapi/api.go:1571-1626`: `GetTransactionReceipt` performs `GetTransaction`, then separately `GetReceipts(ctx,blockHash)`, indexes `receipts[index]`, and serializes `blockHash`, `blockNumber`, `status`, `transactionHash` from the earlier lookup and receipt without a second canonicality check. `/electroneum-sc/eth/api_backend.go:185-187` resolves receipts by the **earlier block hash**, not current canonical number.
4. Possible race: lookup returns tx in block A; chain switches canonical height to competing B; receipts for A remain accessible by hash; adapter returns A receipt. This is **not established**: reorg may serialize reads or remove old receipts, and a client may independently revalidate canonicality.
5. Alternative explanations: (a) real backend permits the interleaving, stale receipt returned; (b) backend lifecycle/locking/receipt eviction prevents it; (c) transient stale receipt exists but relying party uses N confirmations and rechecks canonical block hash, so no wrong credit.

## Expected versus observed and strongest counterexample
Expected independent oracle: before reorg A canonical with success and >=N confirmations => credit only if recipient, value, chain ID match; at N-1 => no credit; after reorg B canonical and A orphaned => never credit A, including after restart. Actual **observed this run**: source has a read gap and no explicit post-receipt canonical revalidation. No actual reorg, RPC response, credit decision, or 3-run breach observed. The strongest counterexample is rawdb's canonical-hash check when transaction lookup occurs after reorg, plus an exchange checking block-by-number hash at the credit decision. This does not settle an in-flight race.
