## Executive disposition

**NO NEW VULNERABILITY.** A real loopback TCP/RLPx/ETH66 peer synchronized a three-block, independently validator-quorum-signed QBFT history into a persistent LevelDB receiver. Another real protocol peer then served a four-block, conflicting QBFT-valid history which correctly became canonical. The same block sequences were imported through the shipped `BlockChain.InsertChain` into an independent persistent direct-import control.

**Measured persistent disk allocation for the ETH66 receiver exactly equalled direct-import controls at every required checkpoint**: 1.000x in the initial chain, 1.000x in the competing fork, 1.000x immediately after compaction, and 1.000x after full clean shutdown and database restart. Three repeated sync requests produced three additional ETH66 block-body response messages amounting to 393,627 transmitted message-payload bytes, while the receiver's physical LevelDB allocation changed by **zero bytes**.

The only demonstrated filesystem fatal-exit condition remains P2h's **pre-existing near-full disk** case; P2j did **not** show that an unprivileged peer can drive a healthy storage reserve to exhaustion beyond unavoidable canonical/imported chain data. No finding promotion is authorized.

## Test design and important assumptions

- Production-source snapshot and tree verified against the same immutable Electroneum target. Test files are copied only into a disposable scratch copy; `vendor/electroneum-sc` is unchanged.
- Receiver storage is an independent **128 MiB ext4 loopback filesystem**. Initial available space was **106,135,552 bytes** (about 101.2 MiB), not intentionally pre-filled to ENOSPC.
- Two independent in-memory chains share a genesis and four QBFT validator keys. Chain A contains **3 blocks**, chain B contains **4 blocks** including a different signed transaction at height 1. Both branches have the correct **3-of-4** validator quorum seals, generated by the fixture before any network delivery.
- These validator credentials do **not** belong to the unprivileged network peer threat model. The peer can time or repeat delivery of already-valid chain data; it cannot manufacture an alternative finalized QBFT history merely by sending packets.
- Each block includes a distinct **128 KiB** deterministic pseudo-random transaction payload, not an all-zero compression artifact. Both persistent databases use the same genesis and imported block bytes.
- The remote tip is held until it satisfies the shipped QBFT **5-second future-time acceptance** window before network synchronization; the receiving node's QBFT defaults are not weakened.
- Storage is measured as allocated filesystem blocks (`stat(2).st_blocks * 512`) recursively across LevelDB regular files. This is a physical point-in-time measurement; timing, WAL buffering, LSM compaction and runner filesystem behavior can vary between runs.

## Persistent integrity oracle

After stopping both remote servers, the receiver protocol handler, QBFT engines and database handles, the test reopened the *same* LevelDB directories using shipped QBFT defaults. For **both** the ETH66 receiver and direct-import control:

- The head remained the four-block branch B.
- B1's signed transaction retained a successful matching canonical receipt.
- A1's orphaned transaction receipt was absent from canonical receipt lookup.
- The reopened databases had the same measured allocated size (**954,368 B**).

Markers: `R_P2J_MULTIHEIGHT_A_BASELINE`, `R_P2J_DUPLICATE_REPLAY_OBSERVATION`, `R_P2J_ABANDONED_FORK_BASELINE`, `R_P2J_OLD_FORK_REPLAY_CONTROL`, `R_P2J_COMPACTION_MATRIX`, `R_P2J_RESTART_PERSISTENCE_PASS`, `R_P2J_P2J_VALIDATED`.

**Counterexamples / limits:** This is one small 3+4 block scenario on one filesystem, not a full long-horizon storage growth bound. The older, noncanonical peer was **not readmitted**, so direct old-fork body replay was not tested after the branch switch. No test demonstrated an untrusted peer could force a high-frequency supply of new QBFT-finalized branches. Point-in-time allocated bytes cannot alone quantify write endurance, IOPS pressure, temporary kernel page cache or compaction CPU. Independent no-peer and direct-import controls minimize, but do not eliminate, baseline variability.

## Next security-relevant hypothesis

To advance G6 beyond the current negative result, the peer must cause durable storage growth under **solely lower-authority choices**, not merely relay unavoidable valid canonical history or a contrived validator-quorum-signed fork. The next experiment should use a bounded realistic long chain and test old-block unsolicited responses, ETH66 request-ID collisions/replays, malformed-but-decodable receipt batches, and very large **already-valid** branches, enforcing a no-quorum-key attacker model and recording discards, peer drops, compaction/I/O and durable delta after restart.

If the network rejects unsolicited responses or the disk grows only in proportion to accepted canonical data, keep this case classified as **operational storage-capacity behavior**, not a bounty-ready remote denial-of-service vulnerability. Do not run on third-party/public nodes.
