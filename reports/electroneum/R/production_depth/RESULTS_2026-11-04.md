### Shipped `bind.WaitMined` client-integrity impact

Campaign [41770009976](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41770009976) tests a concrete shipped consumer rather than a hypothetical application. The path is the real in-process JSON-RPC server → `ethclient.Client.TransactionReceipt` → `bind.WaitMined`. Neither shipped helper performs a canonical block-hash recheck before `WaitMined` returns a successful receipt.

The deterministic sensitivity fixture performs a real `BlockChain.InsertChain` reorg between the receipt API's transaction lookup and receipt read. The returned receipt belongs to the old block even though that height already maps to the competing canonical block when `WaitMined` returns.

Verified markers:
- `R_WAITMINED_STALE_MINED_SIGNAL`
- `R_WAITMINED_CANONICAL_RECHECK_REJECTS_PASS`
- `R_WAITMINED_POST_REORG_NOTFOUND_CONTROL_PASS`
- `R_WAITMINED_G7_CLIENT_INTEGRITY_IMPACT_PASS`

Observed deterministic case:
- returned receipt block: `0x2118fb81fc1ac90e51dbe4f2dd06c1e583764dbcbd462ef849bed8a3053637a8`
- canonical block at the same height when the helper returned: `0xa074042bbe13cf87c5ce8ec218ff5e03616568794c13a9a65883a8a413acb60b`
- immediate canonical header query through the **same shipped `ethclient`** detected the mismatch;
- a subsequent `TransactionReceipt` call returned `NotFound`, proving the stale success is the TOCTOU window rather than persistent orphan exposure.

**Concrete impact:** the shipped `bind.WaitMined` helper can signal “mined” using a receipt that is already noncanonical. This is a client-integrity consequence. It is not evidence of theft, authorization bypass, or financial loss. A consumer that immediately verifies `receipt.BlockHash` against the canonical header at `receipt.BlockNumber` rejects the stale result.

### Candidate canonicality guard is not an atomic fix

Campaign [41770476077](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41770476077) tests the obvious remediation: after reading the receipt, read the canonical block at that height and reject the receipt if its block hash differs.

The candidate guard was injected **only into disposable scratch source**. R then scheduled the real competing-chain import immediately after the guard obtained the old canonical block, but before the guard compared that block and returned. The guard therefore compared a now-stale captured block object to the old receipt hash and accepted it even though the live canonical mapping had already changed.

Markers:
- `R_CANONICAL_GUARD_RESIDUAL_TOCTOU_OBSERVED`
- `R_CANONICAL_GUARD_NOT_COMPLETE_FIX_PASS`

Workflow triage:
- `candidate_post_read_canonical_guard=INCOMPLETE`
- `residual_race=REORG_AFTER_CANONICAL_READ_BEFORE_RETURN`
- `mitigation_requirement=ATOMIC_CHAIN_VIEW_OR_CLIENT_REORG_AWARE_SEMANTICS`

**Counterexample:** adding another canonical read does not remove the concurrency problem; it creates a later check/use boundary. It can reduce the exposure window and is useful as defense-in-depth, but it cannot promise “canonical at return” without synchronization/snapshot semantics that cover the complete decision boundary. The client-side check demonstrated in P1f has the same limitation as a strict guarantee: it detects the reproduced case, but a later reorg is always possible.

Remediation implication:
- do **not** merge the one-shot guard and call E-RPC-004 closed;
- first define the API guarantee: point-in-time receipt lookup versus reorg-stable/canonical-at-return semantics;
- if canonical-at-return is required, expose an atomic chain snapshot/read transaction or coordinate receipt lookup with the chain reorg lock;
- if the API remains point-in-time/reorg-prone by contract, make `WaitMined`/consumer guidance explicitly reorg-aware and use confirmation/finality semantics instead of treating one receipt as irreversible.






### Contract semantics and final classification

The audit contract's invariant E concerns misrepresenting transaction/block reality to exchanges or third parties. P1f satisfies the **mechanism** side of that invariant under the tested conflicting-branch condition: a shipped helper returns a receipt whose block is already noncanonical when observed immediately after return.

However, two boundaries prevent overclaiming:

1. `bind.WaitMined` is documented only as waiting for a transaction to be **mined**. It does not promise irreversible finality or reorg-stable inclusion. The RPC layer separately defines a `finalized` block selector.
2. The end-to-end QBFT reproducer requires a valid committed-seal quorum. P1d shows an ordinary peer without that authority cannot manufacture the tested finalized competing block.

Therefore the correct split classification is:

| Actor / claim | R disposition |
|---|---|
| Source receipt lookup/read consistency race | **CONFIRMED** |
| Shipped `WaitMined` can surface stale noncanonical receipt during that race | **CONFIRMED** |
| Quorum-authorized conflicting QBFT branch → devp2p → race → stale client result | **CONFIRMED, conditional** |
| Ordinary unauthenticated devp2p peer can create the finalized conflicting branch | **DISPROVEN in tested model** |
| `WaitMined` promises finality and violates that promise | **NOT SUPPORTED by shipped contract** |
| Theft / monetary loss / authorization bypass / consensus-finality compromise caused by the receipt race itself | **NOT ESTABLISHED** |

This means E-RPC-004 should not be presented as an arbitrary remote-peer exploit. Its security relevance is conditional on a much stronger consensus-authority/reorg precondition; its independently demonstrated value is a reorg-consistency/client-integrity hazard and a warning against treating a single mined receipt as irreversible.


## P2 — Persistent sync checkpoint / restart consistency

A real LevelDB database is closed and reopened after explicit sync-stage checkpoints. The corrected stage model follows legitimate head-marker ordering: header head may lead; fast head advances when body+receipts are available; full head advances only after complete body+receipts+lookup state.

Verified restart matrix:

| Stage | Full head | Fast head | Header head | Body | Receipts | Tx lookup |
|---|---:|---:|---:|---|---|---|
| header_head_only | 0 | 0 | 1 | no | no | no |
| receipt_before_body | 0 | 0 | 1 | no | yes | no |
| body_before_receipt | 0 | 0 | 1 | yes | no | no |
| body_receipt_no_lookup | 0 | 1 | 1 | yes | yes | no |
| complete | 1 | 1 | 1 | yes | yes | yes |

Additional controls:
- unclean-shutdown marker persisted across reopen;
- body transaction root matched the stored header;
- receipt root matched the stored header;
- incomplete receipt/body combinations were not exposed as fully derived receipts;
- transaction lookup did not become usable before the lookup stage;
- deliberate persistent body-RLP corruption was detected by the oracle.

Marker: `R_PERSIST_CORRUPTION_CONTROL_DETECTED_PASS`.

**Counterexample / rejected false finding:** the first fixture advanced the **full block head** before its body existed and triggered a restart panic. That state was created manually and violated normal sync head ordering. It is retained as evidence that arbitrary DB corruption can break recovery, but it is **not** classified as a network-reachable source defect.

## Bottom line

- **E-RPC-004 is a verified source/client reorg-consistency defect with an explicit actor boundary.** The stale-receipt race survives a real `BlockChain`/`EthAPIBackend`, the real downloader, and real TCP/RLPx/ETH66 transport. A 3-of-4 quorum-authorized QBFT competing branch also reaches it end-to-end.
- **The ordinary unauthenticated-peer attack path is not established; the tested consensus gate rejects it.** Finalized competing blocks require `ceil(2N/3)` unique validator committed seals: 3/4 and 5/7 imported, while 2/4, 4/7, duplicate seals and outsider signatures were rejected.
- **Concrete shipped-client integrity impact is confirmed, but the remediation must be reorg-aware.** `bind.WaitMined` can return an already-noncanonical receipt as mined during the TOCTOU window. A canonical header-hash recheck detects the reproduced stale result, but P1g proves that a one-shot recheck is itself racy and is not a complete atomic fix.
- **No theft, authorization bypass, monetary loss, or receipt-race-created consensus-finality compromise is demonstrated.** The strongest end-to-end reproducer already assumes validator-quorum authority, and `WaitMined` documents mining rather than irreversible finality. That is materially different from an ordinary remote peer exploit.
- **No new confirmed findings** arose from P2 persistence, P3 parser budgets or P4 priority consensus integration.
