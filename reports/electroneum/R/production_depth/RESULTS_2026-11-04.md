## P1 — Real BlockChain / EthAPIBackend reorganization

The test constructs a real in-process `core.BlockChain`, a real `eth.EthAPIBackend`, a signed transaction and a validated longer competing chain. The fork is imported through `BlockChain.InsertChain`, i.e. the same validated import primitive used downstream of synchronization. This is **peer-equivalent block import**, not a devp2p transport reproduction and not a QBFT adversary simulation.

### Deterministic sensitivity control

A controlled scheduling wrapper triggers the validated reorg between the real backend's transaction lookup and receipt read. The original receipt is returned after the canonical mapping changed.

Markers:
- `R_FULL_BACKEND_TOCTOU_ORACLE_MISMATCH`
- `R_FULL_DOWNSTREAM_RECHECK_REJECTS_STALE_RECEIPT_PASS`

The consumer-side canonical hash recheck correctly rejects the stale response, establishing a concrete mitigating counterexample.

### Unmodified backend race campaign

No delay wrapper was used around the RPC backend. Across **24 trials**, old-chain depths 2/4/7 and two query workers:

- Total receipt calls: **380,464**
- Old-receipt responses: **9,723**
- Old receipts whose immediate post-response canonical check already saw the competing block: **44**
- Request intervals that straddled the observed canonical flip and still returned the old receipt: **14**
- Maximum measured observed canonical-flip → response-return interval among those straddled responses: **2,074,585 ns (~2.07 ms)**

Markers:
- `R_FULL_BACKEND_DIRECT_RACE_METRICS`
- `R_FULL_BACKEND_ORDINARY_IMPORT_TOCTOU_OBSERVED`
- `R_FULL_BACKEND_PEER_EQUIVALENT_INSERTCHAIN_CONTROL_PASS`

**Interpretation:** this closes the uncertainty about whether the race survives a real `BlockChain` + `EthAPIBackend` and ordinary validated competing-chain import. It does **not** establish a production probability: CI scheduling, hardware, chain size and query concurrency are artificial. It also does not prove an untrusted network peer or below-threshold QBFT adversary can force the reorg or timing.

Finding gate:

- G6 production reachability: **PARTIAL** — full backend / validated `InsertChain` established; external devp2p/QBFT adversary path OPEN

## P2 — Persistent sync checkpoint / restart consistency

A real LevelDB database is closed and reopened after explicit sync-stage checkpoints. The corrected stage model follows legitimate head-marker ordering: header head may lead; fast head advances when body+receipts are available; full head advances only after complete body+receipts+lookup state.

Verified restart matrix:

| Stage | Full head | Fast head | Header head | Body | Receipts | Tx lookup |
|---|---:|---:|---:|---|---|---|
| header_head_only | 0 | 0 | 1 | no | no | no |
| receipt_before_body | 0 | 0 | 1 | no | yes | no |
| body_before_receipt | 0 | 0 | 1 | yes | no | no |
| body_receipt_no_lookup | 0 | 1 | 1 | yes | yes | no |
| complete | 1 | 1 | 1 | yes | yes | yes |

Additional controls:
- unclean-shutdown marker persisted across reopen;
- body transaction root matched the stored header;
- receipt root matched the stored header;
- incomplete receipt/body combinations were not exposed as fully derived receipts;
- transaction lookup did not become usable before the lookup stage;
- deliberate persistent body-RLP corruption was detected by the oracle.

Marker: `R_PERSIST_CORRUPTION_CONTROL_DETECTED_PASS`.

**Counterexample / rejected false finding:** the first fixture advanced the **full block head** before its body existed and triggered a restart panic. That state was created manually and violated normal sync head ordering. It is retained as evidence that arbitrary DB corruption can break recovery, but it is **not** classified as a network-reachable source defect.

### Abrupt process termination without DB close

A follow-up campaign [41764251176](https://github.com/aprashnasuraj-dev/winddeep/actions/runs/41764251176) executes the same checkpoint logic in a child copy of the Go test binary and calls `os.Exit(97)` after LevelDB writes return, deliberately bypassing application DB close/teardown. The parent then reopens the database and starts a real `BlockChain`.

Verified after abrupt exit:
- `receipt_before_body`: full=0, fast=0, header=1
- `body_before_receipt`: full=0, fast=0, header=1
- `body_receipt_no_lookup`: full=0, fast=1, header=1
- `complete`: full=1, fast=1, header=1
- body/receipt commitments and lookup gating remained consistent;
- unclean-shutdown marker remained observable.

Marker: `R_PERSIST_ABRUPT_EXIT_MATRIX_PASS`.

This is an actual unclean process boundary, but still terminates **between completed LevelDB Put operations**. It is not a torn sector, kernel crash, storage-controller loss, or fault injected inside a single LevelDB write.

**Disposition:** valid checkpoint reopen and abrupt-process restart PASS; no new finding. Filesystem/torn-write fault injection remains outside this test.

## P3 — Realistic parser and request budgets

CI compiled separate binaries and ran each under:
- `GOMEMLIMIT=512MiB`
- `GOMAXPROCS=2`
- shell CPU limit: **45 s**
- hard wall timeout: **60 s**
- `/usr/bin/time -v` resource capture

### HTTP JSON-RPC

Near-limit request payload (~4.75 MiB padding):
- known Content-Length: **68.8 ms**
- unknown/chunked-style Content-Length: **70.7 ms**
- measured allocation delta: ~**21.8 MB**
- process maximum RSS: **56,632 KiB (~55.3 MiB)**

Unknown-length payload above the nominal 5 MiB codec limit did **not** yield a successful valid RPC response:
- HTTP recorder status: **200**
- request handling: **30.2 ms**
- allocation delta: ~**16.8 MB**

The 200 status is transport behavior from truncated JSON decoding, not evidence the oversized RPC method executed successfully. A stricter 413 policy for unknown-length/chunked requests would be an API-hardening choice, not a demonstrated security defect from this campaign.

### Nested ABI `bytes[][]`

- ~1 MiB requested payload, encoded **1,067,072 bytes**: **256.7 µs**, allocation delta **97,608 bytes**
- ~4 MiB requested payload, encoded **4,268,096 bytes**: **647.3 µs**, allocation delta **387,672 bytes**
- process maximum RSS: **28,552 KiB (~27.9 MiB)**
- giant semantic offset mutation rejected inside the dedicated short wall-time oracle.

### Raw transaction and receipt/log RLP

Signed dynamic-fee transaction:
- raw size **2,097,261 bytes**
- decode + canonical hash check: **233.4 µs**
- allocation delta **2,098,280 bytes**

Receipt/log structure:
- encoded size **2,113,049 bytes**
- **256 logs**
- decode: **814.7 µs**
- allocation delta **4,325,784 bytes**
- canonical RLP re-encode stable

Process maximum RSS: **32,164 KiB (~31.4 MiB)**.

**Disposition:** all tested budgets pass. These tests do not prove safety for unbounded internal readers or arbitrary endpoints that bypass the HTTP size limit.

## P4 — Priority transaction, fork transition, actual execution and reorg

The fixture crosses two changes at block 1:
- priority-transactor registry address changes from old registry to new registry;
- `FutureForkBlock=1` activates the sender-bound priority signature scheme.

The actual block contains a signed priority transaction authorized by the **new** registry and future-fork signer. The transaction is executed by the real `StateProcessor` through `BlockChain.InsertChain`.

Verified:
- `R_PRIORITY_ACTUAL_BLOCK_EXECUTION_TRANSITION_PASS`
- new registry active; old registry privilege absent;
- same transaction accepted by txpool while it is admitting the next block;
- strict execution ↔ txpool parity oracle: `R_PRIORITY_POOL_EXECUTION_STRICT_PARITY_PASS`;
- longer competing chain inserted and pool reset;
- pending tx remained tracked;
- dropped block transaction reinjected;
- txpool internal index/nonces remained consistent;
- `R_PRIORITY_REORG_POOL_STATE_PASS pending_nonce=2 has_dropped=true`.

Workflow triage: `candidate=NONE`.

**Disposition:** no priority signature/registry/pool parity defect reproduced. Live multi-validator QBFT message flow remains a separate layer.

## Failure-triage record

The following red runs were **not target findings**:

1. P1 initial run: literal `\n` in Go imports → compile error.
2. P2 initial run: invalid full-head-before-body checkpoint model → recovery panic under manually inconsistent DB state.
3. P3 first runs: test-only `core/types -> trie -> core/types` import cycle plus malformed literal newline in replacement.
4. P4 first run: registry genesis accounts had nil balances → fixture panic.
5. P4 later red runs: all substantive execution/parity/reorg assertions passed; test teardown closed the DB before stopping the blockchain.

Each was corrected as a harness/model problem before final classification.

## Bottom line

- **Existing E-RPC-004 is materially stronger:** the stale-receipt race is reproduced through a real `BlockChain`/`EthAPIBackend` both during direct validated competing-chain import and through the real downloader `Peer` + `LegacySync` path.
- **No new confirmed findings** from P2 persistence, P3 parser budgets or P4 priority consensus integration.
- Next evidence gap for E-RPC-004 is no longer the backend itself; it is **external transport/consensus adversary reachability and downstream impact**: real TCP/RLPx/devp2p ingress, realistic QBFT reorg/finality conditions, and a concrete consumer that fails despite normal confirmation/canonicality controls.
